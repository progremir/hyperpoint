# Settings window

Settings… (⌘,) opens a preferences window with a toolbar of five tabs: General, Hyper Key, Buttons, Scrolling and Devices. Each tab is one page at a fixed 640 pt width, and the window's height animates to the page. Pages are two-column forms: right-aligned labels on the left, controls and a small explanation on the right, dividers between groups. Every edit saves to `~/.config/hyperpoint/config.json` through the same parser as a hand edit, and the engine re-applies.

## Sub-features

- `settings-open` opens and activates the window from the menu, on the tab the user had open last.
- `settings-tabs` renders each tab and switches like a native preferences window: the new page stays hidden while the window animates to its height over 0.18 s, then shows. Another mouse's taller page hides the same way. A page that grows or shrinks where it is (a rule added or removed) stays in view while the window follows, its bottom revealed as the window grows. It is never clipped or scrolling unless it is taller than the screen.
- `settings-device` shares one Device popup between Buttons and Scrolling. New mice say "(New)"; ignored devices are not listed.
- `settings-rules` edits, adds and removes profile rules with pickers limited to valid choices.
- `settings-listen` adds a rule for the button the user presses or the thumb wheel the user turns. Add Rule listens for 10 s, the pressed control gets a rule on its first free trigger, and the button's menu adds one without pressing. A rule's Button cell listens the same way and moves that rule to the pressed button.
- `settings-graph` edits the speed curve by dragging points, saving on mouse-up.
- `settings-setup` sets a new device up from the Devices, Buttons or Scrolling tab: the button applies the best preset, and its menu offers the other presets, an empty profile for a mouse and a copy of another profile. On the Hyper Key tab, switching on a new keyboard applies the keyboard preset to it.
- `settings-devices` renames a profile, forgets it after a confirmation, ignores a new device and stops ignoring one.
- `settings-save` writes the file and the engine re-applies; the window is read-only while the file is invalid.

## How to get to it (user POV)

- Menu bar icon › Settings… or ⌘, while the menu is open.
- Toolbar: General (login item, how to grant permissions, config file, log), Hyper Key (on/off switch, key, keyboards, how it works), Buttons (Device popup, status and Re-apply, rules, gestures), Scrolling (Device popup, smooth scrolling, speed graph, glide, hold to scroll, not yet available), Devices (every device, Set Up, Forget, Ignore, Stop Ignoring).

## Driving it with verify.sh

Preconditions:

- Hyperpoint running and settled.
- A copy of the user's config saved to the evidence directory before any edit.

- **Every tab renders.** Run `verify.sh settings-shots`. Under `settings/` it writes one PNG per tab at the window's own size, toolbar included, then the same set again in dark mode: `01-general.png`, `02-hyper-key.png`, `NN-buttons-<mouse>.png` and `NN-scrolling-<mouse>.png` for each mouse (such as `03-buttons-mx-master-3.png`), and `NN-devices.png` last, each with an `-dark.png` twin. A page taller than the screen gets a second PNG, `NN-name-end.png`, scrolled to its end. Check the PNG heights differ per tab, the selected tab is highlighted, and the Scrolling PNGs show the speed graph, the measured-range labels, the glide sliders and the Hold to scroll section.
- **Tab switches.** Run `verify.sh settings-switches` with the window open or closed. It presses every tab from every other tab (20 switches), switches the Device popup on Buttons and Scrolling to the other mouse and back, and opens Scrolling on the shortest screen when the page is taller than it, then puts the window back on its tab and position. `settings-switches.txt` has every sample and a verdict per change. A switch passes when the height moves one way over 0.1 to 0.3 s, the incoming page is never in the window clipped or with a scroll bar, and it shows within 0.35 s. A Device change passes when the height animates the same way, starts within 50 ms of the first sample that sees the page change, and the page is never clipped or scrolling. The change itself lands about 0.4 s after the press, which is the menu item's selection blink. The page past the screen passes when the window stops at the screen's visible height and the page shows there with a scroll bar. Last, it chooses Record Another Shortcut… from the first Buttons rule whose Do is a shortcut and then presses the recorder's Cancel. Each passes when the window keeps its height and the page shows in every sample, since a capsule taller than the pickers it replaced grew the page and hid it (363 to 517 ms before the fix on 2026-10-26). `verify.sh settings-switches recorders` runs only this. Then it adds a rule from Add Rule's Choose a Button menu, which goes through the same learned rule as a pressed button, and puts the config file back byte for byte, which removes it. Each passes when the height animates one way, starts within 50 ms of the page changing, and the page shows in every sample with no scroll bar (`hidden 0 of N`). Before the fix on 2026-10-26 the page hid for the whole resize on every added rule. `verify.sh settings-switches rules` runs only this.
- **Height animates.** `settings-shots` also prints the window's on-screen heights, sampled every 15 ms (`settings-heights.txt`). Every tab switch and every Device change shows a run of intermediate heights, not a single jump.
- **Last tab.** `defaults write dev.emir.hyperpoint settingsTab devices`, then `settings-shots`: the heights start by settling at the Devices page's height before General's, and `defaults read dev.emir.hyperpoint settingsTab` is `devices` again afterwards.
- **Edit saves.** Ask the user (or drive by accessibility if available) to move "Glide after you stop" and release. `verify.sh log 1m` shows a settings save and `reasons=configChanged … applied` for every device. `diff` the saved copy against the live file: only that key changed (the first save also rewrites formatting and the old speed keys as `curve`).
- **Set up from a fresh install.** With the user's consent, save their config to the evidence directory, run `verify.sh quit`, move the file away and run `verify.sh launch`. The new file has `"devices": []`, and `verify.sh state` shows empty key maps and every MX control native. On Devices each connected device is new with a Set Up button: "Set Up as MX Master 3" for the MX and "Set Up with Hyper Key" for each keyboard. Run `verify.sh set-up "Set Up as MX Master 3"` and `verify.sh set-up "Set Up with Hyper Key"` once per keyboard. The log has `saved devices += … from preset …` for each press, and `verify.sh state` then matches the read-back taken with the user's file. To check the menu, remove a profile from the test file and run `verify.sh set-up "Set Up as MX Master 3" "Nothing yet"`: the file gains a profile with only its match and name. Put the saved file back byte for byte (`cmp`) and check `state` again.
- **Ignore and Forget.** With the user's consent and a device without a profile connected (Karabiner's virtual keyboard is one), Ignore it on Devices: it leaves the Hyper Key list and the Device popup, and `ignored` in the file gains its match. Stop Ignoring removes it again. Forget asks first, then removes the profile.
- **Add Rule listens.** With the user's consent, save their config to the evidence directory and set `HYPERPOINT_VERIFY_RUN=listen-<time>`. Take `verify.sh state` as the baseline. On Buttons with MX Master 3 selected, ask the user to click Add Rule. While the row says "Press a button or turn the thumb wheel on MX Master 3. The left button keeps working.", `verify.sh state` shows 0x52, 0x53, 0x56, 0xC3 and 0xC4 `diverted=yes rawXY=no` (0xD7 is virtual and stays untouched) and `thumbwheel diverted=yes` with `inverted=` as in the baseline. Ask the user to click the gesture button. Mission Control does not open, a highlighted "Gesture button · Hold, move up · Mission Control" row appears, and `state` matches the baseline again. `verify.sh log 2m` shows `listen #N on …`, `listen #N heard control 0xC3`, and `hidpp … reasons=listen applied` twice.
- **Turning the thumb wheel registers it.** Ask the user to click Add Rule. During the listen `verify.sh state` shows `thumbwheel diverted=yes` with its inversion unchanged. Ask the user to turn the thumb wheel in a page that scrolls sideways. The page does not scroll, no rule is added, the Thumb wheel row is highlighted, and the note says "Thumb wheel already has a rule for every way to turn it. Change it here." After the listen, `state` shows `thumbwheel diverted=no` with the baseline's inversion. `verify.sh log 1m` shows `listen #N heard the thumb wheel`. To see the rule added, remove the thumb wheel rule first and repeat: "Thumb wheel · Scroll · Horizontal scroll, reversed" appears. The turn's notification layout comes from Logitech's documentation, not a measurement, so a turn that is not heard, or a journal without that line, points at the decoder in `HIDPPNotice`.
- **Back and the right button.** Start `verify.sh record hold`. Ask the user to click Add Rule and press Back in a browser, then Add Rule and right-click the desktop. The page does not go back and no context menu opens, and the summary's `button events apps saw` has neither press. "Back button · Click · Mission Control" and "Right button · Click · Mission Control" appear. The right button gets a click rule because its scroll rule leaves its click free.
- **Keys from the 2.4G mouse.** On Buttons with 2.4G Mouse selected, start `verify.sh record keys-60` and ask the user to click Add Rule and press the top button that sends Return. During the listen `verify.sh state` shows the 2.4G keyboard service's map empty. The summary has the key at the `in` stage with the keyboard service's sender id, and not at the `app` stage, and `carbonHotkeyFired` stays 0, so no ⌥⇧S was sent. On the preset no rule is added, because Return already clicks and a key that clicks cannot also be held. Its row is highlighted and the note says "Sends Return already has a rule for every way to press it. Change one of these." Afterwards `state` shows both routes back. To see a key rule added, remove the Return rule first and repeat: "Sends Return · Click · Shortcut ⇧⌘4" appears.
- **Choosing without pressing.** Open Add Rule's menu with its arrow and choose Thumb wheel. The note says "Thumb wheel already has a rule for every way to turn it. Change it here." Choose Forward button, and "Forward button · Click · Mission Control" appears with no press. With the MX switched off, Add Rule's click opens the menu and the line under it says "Connect MX Master 3 to add a rule by pressing its button."
- **Change a rule's button by pressing it.** On Buttons with MX Master 3 selected, ask the user to click the capsule in the Top button row's Button cell. The capsule turns red with "Press a button or turn the wheel" and Cancel, Add Rule stays as it is, and `verify.sh state` shows the six diverts. Ask the user to press Back in a browser. The page does not go back, the row becomes "Back button · Click · Shortcut ⇧⌘4" and is highlighted, the rule count is unchanged, and `state` matches the baseline. `verify.sh log 1m` has one `saved devices[…].rules[…] = …`. Click the capsule again and press Back: nothing is saved and no note shows. On 2.4G Mouse, click the Escape row's capsule and press the top button that sends Return: nothing is saved, the Return row is highlighted, and the note says "Sends Return already has a rule for every way to press it. Change one of these." With the MX switched off, the capsule is dimmed, its tooltip says "Connect MX Master 3 to add a rule by pressing its button.", and the chevron beside it still moves the rule. For the capsule's look in every state, light and dark, run `HYPERPOINT_RECORDER_SHOTS=<dir> swift test --filter RecorderFieldShots` and read the PNGs. Put the user's config back afterwards.
- **Every exit gives the buttons back.** Cancel, Esc on the Mac's keyboard, a switch to the Scrolling tab and closing the window each end a listen with no note. Waiting 12 s leaves "No press heard in 10 seconds. Add Rule to try again." Switching the MX off leaves "MX Master 3 disconnected, so Hyperpoint stopped listening." `verify.sh menu "Pause"` leaves "Hyperpoint is paused, so it stopped listening." After each, and after resuming, `state` matches the baseline and `log` shows the listen ending.
- **The left button and saves during a listen.** During a listen, left-click a When picker and change it. The click works, the row keeps listening, `state` still shows the six diverts, and a press afterwards still adds its rule.
- **No divert outlives a crash.** With the user's consent, remove the MX's HID++ rules (keep the right-button rule), click Add Rule, then end the app with `kill -9` while it listens. `state` shows the six diverts. Run `verify.sh launch`. `state` shows every control native. Put the saved config back byte for byte (`cmp`), then `state` matches the baseline.
- **Invalid file.** With the user's consent, write an out-of-range value by hand. The menu shows `Config file has an error`, every tab shows the error and disables editing, and `verify.sh state` is unchanged. Restore the saved copy.

## Gotchas

- `settings-switches` reads the page through Accessibility, which waits for the app's main thread, so it samples the window's height on a separate thread. The window server's height lags the app's by about a frame, so a page's clipping is judged against the app's own window frame.
- Heights the app never set, such as a smooth 423 to 138 over 0.7 s, come from something else scaling windows on screen, such as Mission Control. Rerun when nobody is using the Mac.
- `screencapture` fails in this shell (no Screen Recording grant), so the app renders its own pages. The window is not key during the shots, so the selected tab and the title draw in their inactive colors.
- The first save from the window rewrites the whole file in the app's format. Tell the user before the first edit.
- Hyperpoint has no Dock icon, and raising its window through Accessibility does not make it the active app, so its fields cannot take focus and a posted key event goes to whatever app is frontmost. Activate it with `osascript -e 'tell application id "dev.emir.hyperpoint.dev" to activate'`, check `NSWorkspace.shared.frontmostApplication` is Hyperpoint Dev right before posting any key, and give focus back to the user's app afterwards. Prefer Accessibility actions (`AXFocused`, `AXConfirm`) to key events.
- A listen on a profile without HID++ rules ends by writing every control native, which also clears diverts another app such as BetterMouse left.
- When the listen was the tap's only reason to run, the tap goes away right after the press, so that press's release reaches apps on its own. Apps ignore a release without its press.
- Each listen saves at most one rule. Put the user's config back after the listen checks.
- The engine leaves ignored devices out of its status, so an ignored device is named only if this run of the app saw it as new. Otherwise the Devices tab names it by vendor and product id.
